# MCP 接入需求分析

> 本文档由 AI 基于代码生成，第一版可能有遗漏或偏差。发现问题请直接修改，后续改造中 AI 会持续补全。

**本文档讲什么**：基于本项目特点和当前已知技术债务，分析哪些 MCP 值得接入、为什么、以及现阶段为什么暂不接入。

**目标读者**：项目维护者和未来的 AI 协作规划负责人。

**不是什么**：不是接入指南，不是立即行动清单。

## 1. 值得接的 MCP 清单

### GitHub MCP

| 项 | 说明 |
|----|------|
| **名称** | GitHub MCP（`github` 官方 MCP server） |
| **解决什么问题** | `JobScheduleHelper` 是本项目 2 年内修改频率最高的文件（R-2，22 次改动）。接入 GitHub MCP 后，AI 可直接查询 issue、PR 历史、blame 信息，在修改这个高风险文件时获取完整的改动背景，而不是依赖开发者口头描述。同样适用于 `AdminBiz` 7 个注释占位方法（R-4）——可以直接查看相关 issue 确认实现计划，避免 AI 误判为"可随意实现的空位"。 |
| **重要等级** | **高** |
| **接入成本** | 公司已有 GitHub 组织账号，MCP server 开源可直接部署；需要配置 PAT（Personal Access Token）授权范围（`repo` read 权限即可） |

### Sentry MCP

| 项 | 说明 |
|----|------|
| **名称** | Sentry MCP |
| **解决什么问题** | 本项目触发线程池存在静默丢任务问题（R-1，`JobTriggerPoolHelper` 拒绝策略只打 error 日志），生产环境下任务丢失不可感知。接入 Sentry MCP 后，AI 在修改触发链路时可以直接查询生产错误事件，确认丢任务的实际发生频率，而不是依靠假设。同样适用于 `JobScheduleHelper` bug 热点（R-2）——可以用错误频率数据定位触发边界条件的实际影响范围。 |
| **重要等级** | **高** |
| **接入成本** | 需确认公司是否已有 Sentry 实例；若有，接入成本低（配置 DSN + API Token）；若无，需从零搭建或申请 Sentry Cloud |

### Confluence / 内部 Wiki MCP

| 项 | 说明 |
|----|------|
| **名称** | Confluence MCP（或公司内部 Wiki 对应的 MCP） |
| **解决什么问题** | 本项目有 5 个"代码层面无法确认"的未决问题（见 [architecture.md](architecture.md) 代码之外的未决问题一节），包括 GLUE 版本上限、AI 示例是否有生产依赖方、分布式调度锁替换的架构决策。这些信息通常散落在内部设计文档、会议纪要或架构评审记录中。接入 Wiki MCP 后，AI 可在协作时主动查询这些未决问题的人工决策结论，减少"需要你确认"的停顿次数。 |
| **重要等级** | **高** |

## 2. 典型使用场景

### GitHub MCP 使用场景

**场景 A：修改 `JobScheduleHelper` 前的安全确认**

- **任务**：用户要求修改调度主循环的预读逻辑（如调整预读窗口从 5s 到 10s）
- **示例提示词**：
  ```
  查询 JobScheduleHelper.java 近 6 个月的 PR 合并记录，
  列出每次改动涉及的行范围和 PR 描述，
  我需要评估第 77-148 行的修改风险
  ```
- **产出**：AI 拿到 PR 历史后，可以列出"该文件在 L100-130 范围内有 3 次近期改动，其中 2 次是修复边界条件 bug"，给出比纯代码分析更准确的风险判断

---

**场景 B：确认 AdminBiz 注释方法的实现计划**

- **任务**：用户询问 `jobAdd/jobUpdate/jobDelete` 这 7 个注释占位方法能否实现
- **示例提示词**：
  ```
  搜索本仓库 issue，关键词"AdminBiz"或"jobAdd"，
  看是否有 issue 在追踪这 7 个方法的实现计划
  ```
- **产出**：AI 可以直接告知"存在 issue #XXX 计划在 Q2 实现 jobAdd/jobUpdate"，或"无相关 issue，说明当前无计划，改动前需先开 issue 对齐"

---

**场景 C：验证 `deprecated/` 目录是否安全清理**

- **任务**：用户要求清理 `deprecated/` 下的 20 个死代码文件
- **示例提示词**：
  ```
  查询本仓库近 2 年是否有 PR 引用过
  com.xxl.job.core.deprecated 包下的任何类
  ```
- **产出**：AI 可以给出明确结论"最后一次引用在 2022 年已被 revert，当前无活跃引用，可以安全清理"或"发现 PR #XXX 仍在使用，需先解决依赖"

---

### Sentry MCP 使用场景

**场景 A：量化 TriggerPool 丢任务的实际影响**

- **任务**：用户要修复 `JobTriggerPoolHelper` 的静默丢任务问题（R-1），需要评估影响范围
- **示例提示词**：
  ```
  查询 Sentry 中过去 30 天，
  message 包含"xxl-job, jobTriggerPoolHelper, run is discard"的错误事件数量和分布
  ```
- **产出**：AI 可以告知"过去 30 天共发生 147 次拒绝，集中在每天 10-11 点高峰期，平均丢失 3 个 jobId"，将抽象的代码风险转化为可量化的业务影响

---

**场景 B：定位 `JobScheduleHelper` 边界触发抑制的根因**

- **任务**：生产环境出现任务偶发性不触发，怀疑是时间轮的 ±2 格逻辑
- **示例提示词**：
  ```
  查询 Sentry 最近 7 天，
  message 包含"trigger too fast, repeat trigger suppressed"的告警，
  列出关联的 jobId 和发生时间
  ```
- **产出**：AI 可以将 Sentry 数据与代码逻辑对照，给出"触发抑制集中在整秒边界 ±50ms 内，是 ringThread 的 `now±2` 格与 scheduleThread 预写时间对齐问题"

---

### Confluence MCP 使用场景

**场景 A：查询分布式调度锁的架构决策记录**

- **任务**：用户询问"要不要把 `SELECT FOR UPDATE` 换成 Redis 锁"
- **示例提示词**：
  ```
  搜索内部 Wiki，关键词"xxl-job 分布式调度锁"或"schedule_lock Redis"，
  查看是否有架构评审记录
  ```
- **产出**：AI 可以告知"找到 2024-03 的架构评审记录，结论是：当前 Admin 节点数 ≤ 3，DB 锁等待时长 p99 < 100ms，暂不替换"，避免 AI 和用户重复讨论已有结论的问题

---

**场景 B：确认 GLUE 版本上限的人工决策值**

- **任务**：用户要做 GLUE 版本历史的容量规划
- **示例提示词**：
  ```
  搜索内部 Wiki，关键词"GLUE 版本上限"或"xxl_job_logglue 清理"，
  确认运维侧约定的实际保留版本数
  ```

- **产出**：AI 可以从 Wiki 获取"运维规范明确保留 30 版，mapper XML 的 LIMIT 参数与此对齐"，消除 architecture.md 中标注的"未决问题 1"

## 3. 暂不接入的理由

### 公司 MCP 基础设施成熟度

MCP（Model Context Protocol）生态在 2024 年底才进入快速发展期，多数公司的 MCP 部署处于试验阶段。接入任何 MCP 都需要：

1. **认证与授权**：PAT、OAuth 或 API Key 的申请流程，通常需要安全团队审批
2. **网络连通性**：Claude Code 运行环境与目标系统之间的网络策略放行
3. **MCP Server 托管**：或本地运行、或公司内部托管，需要运维支持
4. **权限边界确认**：AI 通过 MCP 能读到什么范围的数据，需要与数据安全团队确认

这些前置条件通常需要数周到数月完成，与"今天就开始接"的预期不符。

---

### 接入成本与收益的权衡

| MCP | 当前阶段替代方案 | 接入后增益 | 现阶段结论 |
|-----|----------------|-----------|-----------|
| GitHub | `git log`、`git blame`、手动查 PR | AI 可自动拉取上下文，减少手动复制粘贴 | 收益实，但替代方案够用，暂缓 |
| Sentry | 运维手动查询后告知 AI | AI 可直接量化生产影响 | 收益高，但需确认公司是否有 Sentry |
| Confluence | 开发者口头描述未决问题结论 | 消除 5 个"需要你确认"的停顿 | 收益明确，优先级最高，但接入链路最长 |
| Jira/Linear | 开发者手动告知 issue 状态 | 有限增益，替代方案几乎无成本 | 暂不接入 |
| Sourcegraph | 公司内部代码搜索界面 | 跨仓库引用分析 | 需先确认是否有实例 |
| Prometheus | 运维手动提供监控数据 | 将"给公式"变成"给结论" | 接入后价值高，但依赖监控栈存在 |

---

### 什么时候值得接入（触发条件）

以下任一条件满足时，对应 MCP 的接入优先级上升到"立即推进"：

**GitHub MCP**：
- 项目进入密集重构阶段（如 AdminBiz 7 个方法的系统性实现、FIX_DELAY 补全）
- 出现"AI 因缺少 PR 历史上下文给出错误建议"的实际案例

**Sentry MCP**：
- R-1（静默丢任务）被确认为生产事故根因，需要数据驱动修复方案
- 项目有 Sentry 实例且 AI 协作频率超过每周 3 次以上

**Confluence MCP**：
- 未决问题清单（CLAUDE.md 第五节）中任意一条被确认为"频繁影响 AI 协作效率"
- 架构文档迁移到 Confluence 且团队决定以 Confluence 为 SSoT（Single Source of Truth）

**Prometheus MCP**：
- 触发线程池大小需要精确调优（未决问题 4）
- 分布式调度锁替换方案需要数据支撑（未决问题 5）
- 生产环境已有 Prometheus + 相关指标暴露

**Sourcegraph MCP**：
- 公司内部 Sourcegraph 实例已存在且已索引所有相关仓库
- `deprecated/` 清理或 AI 示例模块重构进入实际执行阶段
